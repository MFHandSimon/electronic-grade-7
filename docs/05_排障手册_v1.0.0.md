## §1 开机反复重启（`VL F FAIL` 无限循环）

**现象**：串口每 1–2 秒刷一遍 `VL F FAIL / VL B OK / VL L OK / VL R OK`，一直不停，永远等不到 `READY`。

**原因**：某一路 VL53L0X 初始化失败（`begin()` 返回 false），但代码后面还对它调用
`setMeasurementTimingBudgetMicroSeconds()`，这个调用会死等 I2C 应答，等不到就触发看门狗复位，重启后又重来一遍。

v1.2.0 已经有 `okF/okB/okL/okR` 保护（失败的那路直接不碰、一律返回 `-1`），
所以你**看到 FAIL 但不再重启**是正常的。如果还在反复重启，说明烧的是旧固件，重烧 v1.2.0。

**排 FAIL 的顺序**：

1. 看 `BUS[F_on]` 那行有没有 `29`
   - 没有 `29` → 模块没供电、SDA/SCL 没接、或 XSHUT 没接好
   - 有 `29` 但 `VL F FAIL` → 模块起来了但 `begin()` 失败，多为供电不足或线材接触不良
2. 断电重插那一路的四根线（**杜邦线接触不良是第一大故障源**）
3. 单独用一个模块接到已知好的位置，交叉验证是模块坏还是线坏

## §2 某一路恒 `-1`，或所有距离都是 200–250（俯角问题）

**这是本项目最大的坑，单独一节。**

### 判别

| 数据特征 | 结论 |
|---|---|
| 某一路恒定 `-1`，其他三路正常 | 先查线，再查俯角 |
| **所有**路的距离都在 200–250 之间 | 100% 是俯角 → 在量地面 |
| 前/后恒定 `-1`，左右恒定 240 左右 | 俯角（左右两路先看到地面，前后两路被地面挡死） |
| 读数 573–983 | 正常，成功 |

### 原理

VL53L0X 报的是**视野内最近的物体**。镜头有 11° 左右俯角时，地面落在视野里，
距离约 250mm，比墙（1m 多）近得多 → 永远报地面，墙面数据被彻底挡住。

举高到 1m 复测时：`F/R` 全 `-1`（朝天花板超量程），`L` 仍 600–800，说明确实在打地面。

### 处理

**必须在物理上解决**，软件过滤救不回来（近距假点会把所有墙面点都吃掉）。

1. 找到传感器模块**镜头那一侧**（不是排针那一侧）
2. 在那一侧底部垫 **2–3mm**（纸片、垫片都行），让镜头**微微向上仰**
3. 复测：读数应从 200–250 变成 **500–1000**

> 注意方向：垫错边会变本加厉。垫完一定复测数据，别凭感觉。

## §3 串口读不到数据

按顺序排除：

### 3.1 不要用 `cat`

```bash
cat /dev/ttyS3        # ❌ 永远空白，因为没设波特率
```

必须用 pyserial 明确 115200：

```bash
python3 -c "
import serial,time
s=serial.Serial('/dev/ttyS3',115200,timeout=0.5)
t=time.time()
while time.time()-t<8:
    d=s.read(400)
    if d: print(d.decode(errors='ignore'),end='',flush=True)
"
```

### 3.2 先发后听会错过

```bash
echo "T" > /dev/ttyS3 && cat /dev/ttyS3   # ❌ 发完了才开始听，回复早飞走了
```

正确做法是**先开监听，再按 ESP32 上的 RST**，或者在 python 里同一个会话中先 `write` 再 `read`。

### 3.3 只看到 `READY` 然后没了

`READY` 是 `setup()` 里打印一次的，不是周期输出。看到它说明链路是通的。
要读实时数据就发 `T`（单次）或 `C`（开启流式）。

### 3.4 完全空白

按可能性排序：

1. **没共地**：ESP32 GND 和 RDK GND 必须连
2. **TX/RX 接反**：ESP32 GPIO32(RX) 要接 RDK 的 **TX**；ESP32 GPIO33(TX) 接 RDK 的 **RX**
3. **GPIO32/33 被占**：确认没有别的东西接在这两个脚上
4. **RDK 串口没启用**：`ls -l /dev/ttyS3` 有没有
5. **波特率不一致**：ESP32 用 `RDK.begin(115200, ...)`，一边 115200

## §4 回 `? 未知指令: T`

**原因**：你在跟旧固件说话（旧版没有 `T` 命令），或者 RDK 端脚本的命令名表没收录新命令。

**处理**：
1. 重烧 `esp32_scan_field`（v1.2.0）
2. 如果脚本是自己写的，把 `T`、`Z`、`A`、`D` 补进命令表

## §5 低速电机不转（快衰减问题）

**现象**：PWM 255 能全速转；降到 128 就不转；加「kickStart（先 255 冲 100ms 再降到 128）」
变成「冲刺一下然后不动」。

**原因**：DRV8837 在**快衰减**模式下，低速时电流衰减太快、平均电流太小，扭矩不足。

**解决**：改用**慢衰减**——一个脚常高，另一个脚写 `255 - speed`。
刹车区间电流在 H 桥内回流，低速扭矩大得多。

代码里已经这么写了（v1.2.0）：

```cpp
// 正转
ledcWrite(L_IN1, 255); ledcWrite(L_IN2, 255 - CRUISE_SPEED);
// 反转
ledcWrite(L_IN2, 255); ledcWrite(L_IN1, 255 - CRUISE_SPEED);
// 停止（两脚都 0，别写成 255/255）
ledcWrite(L_IN1, 0);   ledcWrite(L_IN2, 0);
```

`CRUISE_SPEED=128`、`SPIN_SPEED=140`（原地转向要克服更大静摩擦，所以高一点）。

**别改回快衰减**，改回去就是「低速不走、高速太猛」。

## §6 车撞墙了还在转（脚本崩溃）

**现象**：车顶到墙，轮子继续转不停，只能手动断电。

**原因**：固件是「收到 W 就一直走」的状态机，只有收到 `X` 才停。
如果 RDK 脚本解析数据时抛异常崩溃了，`X` 永远发不出去 → 车带着最后一条指令一直冲。

**实测案例**：固件帧改成 5 字段（`f r b l yaw`），脚本还按 4 个字段解析 →
第一帧就 `ValueError` → 崩溃 → 车撞墙继续转。

**解决三件套**：

```python
try:
    # 所有运动逻辑
    s.write(b'W')
finally:
    s.write(b'X')      # 不管怎么退出，必须发停
    s.close()
```

1. **`try/finally` 兜底发 `X`**
2. **解析按 5 个字段**：`v = l[2:].split()`，判断 `len(v) >= 5`，yaw 是 `v[4]/10.0`
3. **加限时**：`while time.time()-t0 < 25` 到点自动停

## §7 转半圈 / 转两圈

| 现象 | 原因 | 解决 |
|---|---|---|
| yaw 只到 170 左右 | 步数写成 24 但每步 30° 的循环中途 `break`；或 `readT()` 返回 `None` 直接退出 | 12 步、`TT()` 重试 6 次 |
| yaw 到 720 左右 | 24 步 × 30° = 720°，转了两圈 | 改成 `for i in range(12)` |

**12 步 × 30° = 360°，这是唯一正确配置。**

另外：跑扫描前**必须发 `Z` 归零**。不归零则 yaw 从上次的累计值开始，目标角永远等不到。

## §8 大量 `-1` 或 `8191`

| 值 | 含义 |
|---|---|
| `-1` | 固件判断 RangeStatus=4（无效测量）或该路初始化失败 |
| `8191` | 超量程原始值（VL53L0X 的 max range 溢出） |

**原因与处理**：

1. **超量程**：>1.9m 开始大量丢数据，1.2m 内最稳 → **车离墙别超过 1m，别放角落**
2. **深色/吸光墙面**：黑色、绒布、深灰 → 换浅色纸板，或贴白纸
3. **强光直射**：阳光/射灯照进镜头 → 遮挡或换位置
4. **镜头脏**：擦干净

## §9 车走偏、一顿一顿

**走偏右**：左右电机的减速比、轮径、地面摩擦不可能完全一致，开环控制下必然偏。
实测全速 0.31 m/s，走 1m 左右会偏 10–20cm，属于正常。
要纠正就得加**航向闭环**（读 yaw，偏差大了给左右轮差速），这是下一步的活。

**一顿一顿**：`slowrun.py` 是脉冲驱动（走 0.3s、停 0.15s），平均约 0.2 m/s。
这是故意的——慢速才能看清测距随位置的变化。想要连续低速就把脉冲去掉，但会更容易撞墙。

## §10 陀螺仪读不到（`r75=FF`）

```
GYRO: 0x68 r75=FF r00=FF r0F=FF
MPU: bias=0 n=0
```

**原因**：I2C 上 0x68 没有应答。

**排查**：
1. `BUS[all_off]` 里有没有 `68`？没有 → 板载陀螺没供电或 I2C 断
2. I2C 四根线（SDA/SCL/3V3/GND）是否被激光模块占用冲突（正常情况可以共用）
3. 板子是不是真的带 MPU6050：`r75=68` 表示是 MPU6050，`r75=70` 是 MPU6500，`r00` 是 QMI8658 的 ID
4. 注意固件用的是 `0x68` 地址 + 直接读写寄存器，不依赖任何库

**航向角精度**：实测 2.5s 转 887°，目测 2.4 圈（864°），误差 2.6%。
说明积分方向对、量程够，长时间跑必须靠重定位纠漂移。

## §11 烧录失败

| 报错 | 处理 |
|---|---|
| `Timed out waiting for packet header` | 按住 BOOT 键再点上传，出现 `Connecting...` 后松手 |
| `Could not open port COMx` | 关掉所有串口工具（Serial Monitor / 串口助手 / 其他 IDE 窗口）再烧 |
| 找不到 COM 口 | 换数据线；装 CH340 / CP210x 驱动；换 USB 口 |
| `Adafruit_VL53L0X.h: No such file` | 库没装，`Tools → Manage Libraries` 搜着装 |
| 编译内存超限 | 正常不会（26% 用量），检查是不是选错板子型号 |

## 最后：什么时候该停下来问人

如果出现下面任意一条，别硬试，直接找人：

- 换了三根线、重插五次，某一路还是 `FAIL`
- 四路全 OK，但 `T` 读到的始终是 `-1`
- 烧录反复失败、换电脑也一样
- 车不受控地一直冲（先断电，再排查）

**记住安全底线**：调试电机时把车架空；跑扫描时人别站在车前方 1m 内；
任何脚本崩溃后第一件事是**断电**，不是去点鼠标。
